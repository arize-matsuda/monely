# テスト戦略

最終更新: 2026-11-07

**目的: 検証を確実に実施させる。** 「動いたはず」で終わらせないため、何をどう確かめるかを手順として固定する。

---

## 1. 方針

### 1.1 v1 はテストフレームワークを入れない

| 判断 | 理由 |
| --- | --- |
| Vitest / Jest を入れない | 画面が 7 つ、純粋なロジックが数本の規模。テストの記述・保守のコストが、得られる安心感を上回る |
| Playwright を入れない | 手で 5 分で確認できる操作を自動化する準備に数時間かかる |
| 代わりにやること | **型検査（`pnpm build`）+ Lint（`pnpm lint`）+ 受入条件の手動確認** を毎回必ず通す |

### 1.2 ただし「必ず手で確認する」ものを決める

自動テストが無い分、**何を確認したら完了とみなすか**を曖昧にしない。[機能要件 §4 の受入条件（AC-1〜AC-12）](../01-requirements/functional-requirements.md#4-受入条件)がその一覧。

### 1.3 導入する条件（将来）

以下のいずれかに当てはまったら、その時点で導入する。

| 条件 | 導入するもの |
| --- | --- |
| 金額・日付の計算ロジックが 3 本以上に増えた | Vitest（`src/lib/money.ts`, `month.ts`, `validation.ts` の単体テスト） |
| 同じ不具合を 2 回出した | その箇所の回帰テスト |
| 画面が 10 を超えた、または手動確認が 15 分を超えた | Playwright（AC-1, AC-4, AC-7, AC-9 の自動化） |
| 自分以外が開発に入る | 上記すべて |

**先に入れない理由**: 使われないテストは腐る。腐ったテストは、無いより悪い。

---

## 2. 品質ゲート（毎回実行）

マイルストーンの完了前、およびコミット前に必ず通す。

```bash
pnpm lint     # Biome。違反 0 であること
pnpm build    # 型エラー・ビルドエラー 0 であること
```

| コマンド | 検出できるもの | 検出できないもの |
| --- | --- | --- |
| `pnpm lint` | 書き方の逸脱、未使用の変数、import の乱れ | 動作の誤り |
| `pnpm build` | 型の不整合、Server/Client 境界の違反、ビルド時の構成エラー | 実行時の誤り、RLS の穴 |

**両方通っても「動く」とは言えない。** 次の手動確認が本体。

## 3. 手動確認の進め方

### 3.1 環境

```bash
pnpm dev          # http://localhost:3000
```

| 事項 | 内容 |
| --- | --- |
| ブラウザ | Chrome の DevTools デバイスモードで **iPhone SE（375 × 667）** を基準にする |
| アカウント | 2 つ用意する（自分のメール + 別のメール。エイリアスでも可） |
| DB | 本番の Supabase プロジェクトに接続している（NFR-O3）。**確認で入れたデータは後で消す** |

### 3.2 マイルストーンごとの確認範囲

| マイルストーン | 実施する受入条件 |
| --- | --- |
| M0 | 画面が表示される。`pnpm lint` / `pnpm build` が通る |
| M1 | [§4.1 スキーマの確認](#41-スキーマと-rls-の確認m1) |
| M2 | AC-1, AC-2, AC-3, AC-11, **AC-9** |
| M3 | AC-4, AC-5, AC-6, AC-7, AC-8, **AC-9（再）** |
| M4 | AC-10, AC-12, **AC-9（再）** |
| M5 | PWA のインストールと全画面起動 |

**AC-9（他世帯のデータが見えない）は M2 以降、毎回実施する。** テーブルや列を足すたびに RLS の穴が開きうる。

### 3.3 記録の付け方

確認の結果は [タスクリスト](../04-development/task-list.md) のマイルストーン欄に記録する。「AC-4 OK（2026-11-xx）」のように日付を添える。**通らなかった項目は、直すまでタスクとして残す。**

## 4. 重点的に確認するもの

### 4.1 スキーマと RLS の確認（M1）

Supabase ダッシュボードで確認する。

- [ ] Table Editor に `households` / `profiles` / `categories` / `transactions` の 4 テーブルがある
- [ ] 4 テーブルすべてに「RLS enabled」が表示されている
- [ ] Database → Functions に `current_household_id`, `create_household`, `join_household`, `handle_new_user`, `touch_updated_at` がある
- [ ] Authentication → URL Configuration の Redirect URLs に `http://localhost:3000/auth/callback` がある
- [ ] マイグレーション SQL を**2 回続けて実行してもエラーが出ない**（冪等性の確認）

SQL Editor で直接確認する場合:

```sql
-- RLS が有効になっているか
select relname, relrowsecurity
from pg_class
where relname in ('households','profiles','categories','transactions');
-- → relrowsecurity がすべて true

-- ポリシーが揃っているか
select tablename, policyname, cmd
from pg_policies
where schemaname = 'public'
order by tablename, cmd;
```

### 4.2 RLS の侵入確認（毎回実施）

**これが v1 で唯一、絶対に省略できない確認。** 漏れたときの被害が他と比べものにならない。

#### 準備

1. アカウント **A** でログイン → 世帯 A を作る → 記録を 1 件入れる（例: 食費 ¥1,280）
2. その記録の ID を控える（一覧から編集画面を開き、URL の `/transactions/<id>` を見る）
3. ログアウト
4. アカウント **B**（別のメールアドレス）でログイン → **世帯 B を新規作成する**（A の招待コードは使わない）

#### 確認

| # | 操作 | 期待する結果 |
| --- | --- | --- |
| 1 | B で `/` を開く | A の記録が 1 件も出ない。支出合計が ¥0 |
| 2 | B で `/?m=<A の記録の月>` を開く | 同様に 1 件も出ない |
| 3 | B で `/transactions/<A の記録の ID>` を直接開く | 「見つかりませんでした」が出る。**金額やカテゴリが一瞬でも表示されない** |
| 4 | B で `/settings` を開く | メンバー一覧に B のみ。A の名前が出ない。招待コードは B のもの |
| 5 | B のセッションで A の記録を更新・削除しようとする | 失敗する（下記の方法で試す） |

#### #5 の試し方

編集画面が開けないため、Server Action を直接呼ぶ必要がある。B でログインした状態のブラウザの DevTools コンソールから、編集フォームの POST を模倣するのが最も簡単。

より確実な方法として、SQL Editor で B のユーザーとして実行する:

```sql
-- B のユーザー ID を調べる
select id, email from auth.users;

-- B のセッションを模倣して A の記録に触れるか確認する
begin;
  set local role authenticated;
  set local request.jwt.claims = '{"sub":"<B のユーザー ID>","role":"authenticated"}';

  -- 0 行であること
  select count(*) from transactions where id = '<A の記録の ID>';

  -- 0 行更新であること
  update transactions set amount = 1 where id = '<A の記録の ID>';

  -- 0 行削除であること
  delete from transactions where id = '<A の記録の ID>';
rollback;
```

`begin` / `rollback` で囲むので、実行しても DB は変わらない。**`rollback` を忘れない。**

#### 失敗したときの対応

1 つでも期待どおりでなかった場合、**他の作業を止めて先に直す**。原因は次のいずれかが多い。

| 症状 | 疑う箇所 |
| --- | --- |
| 他世帯のデータが見える | RLS が有効になっていない、またはポリシーの条件が `true` に近い |
| `profiles` の取得で無限再帰のエラー | `current_household_id()` に `security definer` が付いていない |
| 更新が通ってしまう | UPDATE ポリシーの `with check` が無い |
| 他世帯のカテゴリ・メンバーを記録に紐付けられる | アクション内の所属確認が無い（RLS では防げない。[API設計 §4.3](../02-design/api-design.md#43-記録srcactionstransactionsts)） |

### 4.3 金額と日付の確認（M3）

計算のずれは静かに起きるため、必ず**手計算と突き合わせる**。

- [ ] 1 件ずつ金額をメモしながら 5 件入れ、支出合計が手計算と一致する
- [ ] 収入を 1 件入れ、差額 = 収入 − 支出 になっている
- [ ] 月末（例: 10月31日）と月初（11月1日）の記録が、それぞれ正しい月に入る
- [ ] 月を移動しても、前の月の記録が混ざらない
- [ ] `0`、`-100`、`12.5`、空文字、`1280円`、`１２８０`（全角）を金額に入れて保存を試す → すべて弾かれる
- [ ] 9,999,999 を超える金額が弾かれる
- [ ] 日付を未来（来月）にして保存できる。その月に表示される

**全角数字のケースを必ず試す。** スマホの日本語キーボードでは全角が混入しやすい。

### 4.4 入力速度の確認（M3 / M4）

ストップウォッチで測る（NFR-P3, NFR-U2）。

- [ ] 起動から保存完了まで **10 秒以内**
- [ ] タップ数（キーボードの打鍵を除く）が **5 回以内**

超えている場合は、どの操作で時間を使っているかを書き出してから UI を直す。

### 4.5 スマホでの確認（M4）

- [ ] 幅 375px で横スクロールが発生しない
- [ ] 幅 320px でも崩れない
- [ ] 下部タブが固定され、セーフエリアに潜らない
- [ ] 金額欄をタップすると数値キーボードが開く
- [ ] タップ対象が 44px 以上（DevTools で計測）
- [ ] OS をダークモードにすると配色が追従し、文字が読める
- [ ] 実機（iPhone）で 1 件記録できる

### 4.6 エラー時の確認（M3）

- [ ] DevTools の Network を Offline にして保存 → エラーが表示され、**入力内容が残っている**
- [ ] 存在しない ID で `/transactions/xxxx` を開く → 「見つかりませんでした」
- [ ] `/?m=abc` を開く → 当月が表示される（エラーにならない）
- [ ] 無効な招待コードで参加を試す → 招待コード欄にエラーが出る

### 4.7 PWA の確認（M5）

- [ ] スマホのブラウザで「ホーム画面に追加」ができる
- [ ] 追加したアイコンから起動すると、アドレスバーのない全画面で開く
- [ ] アイコンが意図したものになっている
- [ ] 起動後にログイン状態が保持されている

## 6. 将来の自動化（導入時の優先順）

導入条件（§1.3）を満たしたときに、この順で入れる。

| 順 | 対象 | 道具 | 理由 |
| --- | --- | --- | --- |
| 1 | `src/lib/money.ts`, `month.ts`, `validation.ts` | Vitest | 純粋関数で、テストが書きやすく壊れにくい。ずれると全画面に影響する |
| 2 | RLS の侵入確認（§4.2） | SQL スクリプト | 毎回手で実施している手順をそのまま SQL にできる。**最も価値が高い** |
| 3 | AC-4（記録の登録）、AC-7（月の移動） | Playwright | 回帰が起きやすい中核の操作 |
| 4 | AC-1〜AC-3（認証と世帯） | Playwright | メールの受信を伴うため自動化が難しい。最後 |

**2 を 1 より先に入れてもよい。** RLS の確認は手順が決まっており、かつ失敗の代償が最も大きい。
