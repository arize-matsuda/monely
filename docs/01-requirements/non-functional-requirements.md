# 非機能要件

最終更新: 2026-11-07

**目的: 品質基準を統一する。** 「速い」「安全」といった言葉を、判定できる形にしておく。

ID の体系: `NFR-S`=セキュリティ / `NFR-P`=性能 / `NFR-U`=使い勝手 / `NFR-D`=データ / `NFR-A`=可用性 / `NFR-C`=互換性 / `NFR-M`=保守性 / `NFR-O`=運用

---

## 0. 優先順位

品質特性が衝突したときの優先順位。**上が優先。**

1. **セキュリティ**（他世帯のデータが見えない）
2. **使い勝手**（記録が速い）
3. **データの正しさ**（金額・日付がずれない）
4. 性能
5. 可用性
6. その他

利用者が数人の個人アプリなので、可用性やスケールより「漏れない」「速く入力できる」を取る。

---

## 1. セキュリティ（NFR-S）— 最優先

| ID | 要件 | 判定方法 |
| --- | --- | --- |
| NFR-S1 | **他の世帯のデータは一切見えない。** DB の行レベルセキュリティ（RLS）で担保し、アプリのクエリ条件には依存しない | 4 テーブルすべてで RLS が有効。[AC-9](./functional-requirements.md#ac-9-他世帯のデータが見えないfr-x2-br-12最重要) を手で実施 |
| NFR-S2 | すべての Server Action / Route Handler の中で、認証と世帯の所属を毎回検証する。クライアントから来た世帯 ID は信用しない | 各アクションの先頭に検証がある（コードレビュー） |
| NFR-S3 | Supabase の `service_role` キーをアプリに持ち込まない。公開可能キー（anon / publishable）のみを使う | `grep -r service_role src/` が 0 件 |
| NFR-S4 | キャッシュのキーやタグに個人情報（メールアドレス等）を入れない。平文で保存されるため | コードレビュー |
| NFR-S5 | 認証 Cookie を含むレスポンスを CDN・プロキシにキャッシュさせない | `proxy.ts` で `setAll` の第 2 引数のヘッダを設定している |
| NFR-S6 | 秘密情報をリポジトリにコミットしない | `.gitignore` で `.env*` を除外。`git log -p` に鍵が出ない |
| NFR-S7 | ログイン画面で、メールアドレスの登録有無を外部から判別できない | 送信後のメッセージが常に同一（FR-A6） |
| NFR-S8 | すべての入力をサーバー側で検証する。クライアントの検証は利便性のためのもの | 各アクションに検証がある |
| NFR-S9 | 世帯への参加は招待コードを知っている人のみ。コードは 6 桁（36^6 ≈ 22 億通り）で、総当たりの実用性を持たせない | 設計上の確認。将来は試行回数制限を検討 |

詳細な指針 → [セキュリティガイドライン](../03-guidelines/security-guidelines.md)

## 2. 性能（NFR-P）

| ID | 要件 | 目標値 | 測り方 |
| --- | --- | --- | --- |
| NFR-P1 | 一覧（`/`）の表示完了 | 1.5 秒以内（通常のモバイル回線） | DevTools の Network / 体感 |
| NFR-P2 | 記録の保存から一覧への反映 | 1 秒以内 | 体感 |
| NFR-P3 | 記録の登録操作全体（起動〜保存） | **10 秒以内** | ストップウォッチ（UC-1） |
| NFR-P4 | 月次一覧のクエリ | インデックスに乗ること | `explain` で `transactions_household_occurred_idx` が使われる |
| NFR-P5 | 想定データ量での劣化がないこと | 1 世帯あたり年 3,000 件、5 年で 15,000 件を想定 | 件数を投入して体感確認（v2 以降） |

**やらないこと**: 細かな最適化（`use cache` によるプリフェッチ、画像の最適化、バンドル分割）は v1 で追わない。利用者が数人で、実測で困っていない段階での最適化は複雑さの持ち込みにしかならない。

---

## 3. 使い勝手（NFR-U）

| ID | 要件 | 目標値 |
| --- | --- | --- |
| NFR-U1 | スマホ縦画面を基準に設計する | 幅 375px で横スクロールが出ない |
| NFR-U2 | 記録の登録に必要なタップ数 | キーボード入力を除き **5 回以内** |
| NFR-U3 | 金額入力で数値キーボードが開く | `inputMode="numeric"` を指定 |
| NFR-U4 | 主要な操作ボタンを親指の届く画面下部に置く | 下端から 160px 以内 |
| NFR-U5 | OS のダークモード設定に追従する | `prefers-color-scheme` で切り替わる |
| NFR-U6 | 文字と背景のコントラスト | WCAG AA（本文 4.5:1、大きい文字 3:1）以上 |
| NFR-U7 | タップ対象の大きさ | 44 × 44px 以上 |
| NFR-U8 | 金額の表示形式 | 3 桁区切り（`¥1,280`） |
| NFR-U9 | 操作の結果が分かること | 保存中はボタンが押せない状態になり、完了時に画面が変わる |
| NFR-U10 | エラー時に入力内容を失わない | 保存失敗後もフォームの値が残る |
| NFR-U11 | 日本語として自然な文言 | 開発者以外が読んで意味が分かる（家族に確認） |

### アクセシビリティ

| ID | 要件 |
| --- | --- |
| NFR-U12 | すべての入力に `label` が結び付いている |
| NFR-U13 | アイコンのみのボタンに `aria-label` を付ける |
| NFR-U14 | フォーカスが見える（`:focus-visible` のスタイルを消さない） |
| NFR-U15 | 色だけで情報を伝えない（収入は色 + `+` 記号の両方で示す） |

**v1 で追わないこと**: スクリーンリーダーでの完全な操作検証、キーボードのみでの全操作。利用者 2〜3 人が全員スマホのタッチ操作であることが分かっているため。構造的に正しい HTML を書くことで素地だけ残す。

## 4. データ（NFR-D）

| ID | 要件 | 理由 |
| --- | --- | --- |
| NFR-D1 | 金額は整数（円）で保持する。浮動小数点を使わない | 合計の丸め誤差を構造的に起こさない |
| NFR-D2 | 日付は日付型（時刻なし）で保持する | タイムゾーンのずれで前日・翌日に動かないようにする |
| NFR-D3 | 作成時刻・更新時刻を記録する | 同じ日付の並び順の決定、不具合調査 |
| NFR-D4 | 参照整合性を DB の外部キーで担保する | アプリのバグでデータが孤児にならない |
| NFR-D5 | メンバーが抜けても記録自体は残る | 家計の履歴が消えると意味がない（`on delete set null`） |
| NFR-D6 | 削除は物理削除。論理削除フラグを持たない | 単純さを取る。カテゴリのみ `archived` で例外扱い |
| NFR-D7 | バックアップは Supabase の機能に依る。自前のエクスポートは v1 では作らない | 無料プランの自動バックアップで、失っても再入力可能な量 |

## 5. 可用性（NFR-A）

| ID | 要件 | 水準 |
| --- | --- | --- |
| NFR-A1 | 稼働率の目標 | **定めない。** 個人用途であり、数時間止まっても再入力できる |
| NFR-A2 | Supabase に障害がある場合 | アプリは「読み込めませんでした」を表示して再試行を促す。データの不整合を起こさない |
| NFR-A3 | オフライン動作 | **対応しない**（通信前提）。圏外では保存に失敗し、入力内容は画面に残る |
| NFR-A4 | 障害時の復旧 | 開発者本人が対応する。監視・通知の仕組みは作らない |
| NFR-A5 | データ消失の許容 | 許容しない。消失が疑われる場合は Supabase のバックアップから復旧する |

## 6. 互換性（NFR-C）

| ID | 対象 | 水準 |
| --- | --- | --- |
| NFR-C1 | iOS Safari | 最新 2 バージョン |
| NFR-C2 | Android Chrome | 最新 2 バージョン |
| NFR-C3 | PC Chrome | 最新版（開発・確認用） |
| NFR-C4 | PWA | ホーム画面に追加でき、全画面（standalone）で起動する（M5） |
| NFR-C5 | 画面幅 | 320px〜。PC では最大幅を設けて中央寄せ |
| NFR-C6 | その他のブラウザ（Firefox, Edge, IE） | 動作を保証しない |

---

## 7. 保守性（NFR-M）

| ID | 要件 | 判定方法 |
| --- | --- | --- |
| NFR-M1 | `pnpm lint`（Biome）に違反がない | CI ではなく手元で実行 |
| NFR-M2 | `pnpm build` が警告なしで通る | 同上 |
| NFR-M3 | TypeScript の型エラーがない。`any` を使わない | `pnpm build` / `grep -rn ": any" src/` |
| NFR-M4 | 仕様を変えたら同じコミットで `docs/` を更新する | コミットの中身 |
| NFR-M5 | 設計判断は ADR に残す | [05-decisions/](../05-decisions/) |
| NFR-M6 | 1 ファイルの行数の目安 | 300 行以内。超えたら分割を検討 |
| NFR-M7 | 依存パッケージを増やさない | 追加する場合は ADR を書く |

**NFR-M7 の意図**: 個人開発では依存の更新が止まった時点で負債になる。標準機能とフレームワークの機能で足りるものに外部パッケージを入れない。

---

## 8. 運用（NFR-O）

| ID | 要件 |
| --- | --- |
| NFR-O1 | デプロイ先は未定。v1 はローカル（`pnpm dev`）で完成させる。PWA の検証（M5）の前に決める |
| NFR-O2 | 環境は「ローカル」と「本番」の 2 つのみ。ステージングは作らない |
| NFR-O3 | Supabase のプロジェクトは 1 つ（本番用）。ローカルからも同じプロジェクトに接続する |
| NFR-O4 | 秘密情報は `.env.local` に置き、コミットしない。例は `.env.local.example` に置く |
| NFR-O5 | エラーログは Supabase のダッシュボードと開発サーバーのコンソールで確認する。外部の監視サービスは入れない |
| NFR-O6 | DB の変更は `supabase/migrations/` に連番の SQL として残し、Supabase の SQL Editor で適用する |

### NFR-O3 の注意

ローカル開発でも本番の DB に接続するため、**動作確認で入れたテストデータが本番に残る**。確認後に削除するか、v2 で環境を分ける。v1 は自分と家族だけが使うため、この簡略化を受け入れる。

---

## 9. 品質ゲート

マイルストーンを完了とみなす前に、毎回これを通す。

```
pnpm lint     # Biome の違反が 0
pnpm build    # 型エラー・ビルドエラーが 0
```

加えて、M2 以降は毎回 [AC-9（他世帯のデータが見えない）](./functional-requirements.md#ac-9-他世帯のデータが見えないfr-x2-br-12最重要) を手で確認する。RLS は一度書いて終わりではなく、テーブルや列を足すたびに穴が開きうる。
