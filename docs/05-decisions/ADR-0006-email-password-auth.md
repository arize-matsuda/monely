## 背景

[ADR-0001](./ADR-0001-tech-stack.md) §6 でマジックリンク（パスワードなし）を選び、M2 で実装した。実際にログインを試したうえで、**開発者から「普通にメールアドレスとパスワードの方がよかった」という判断があった。**

マジックリンクを選んだ当時の理由は次の 2 つだった。

1. 家族にパスワードを管理させたくない（[プロダクト要件](../01-requirements/product-requirements.md) の課題 B-2）
2. パスワードのリセットフローを作らなくて済む

### 1 については前提が違っていた

課題 B-2（パスワードを増やしたくない）は**開発者が家族の立場を推測して書いたもの**で、実際の要望ではなかった。一方、マジックリンクには実際に使うと分かる摩擦がある。

| マジックリンクの摩擦 | 内容 |
| --- | --- |
| ログインに毎回メールが必要 | アプリを開くたびにメールアプリへ往復する（セッションが切れたとき） |
| 待ち時間がある | メールの到着を待つ。迷惑メールに入ることもある |
| 慣れていない | 「パスワードを入れる」以外の手順を家族に説明する必要がある |

**毎日使うアプリで、ログインのたびにメールを開くのは入力の速さを損なう**（プロダクト原則 1）。

### 2 については別の解がある

マジックリンクを**残したまま**、パスワードを主の認証方式にすればよい。パスワードを忘れたときはマジックリンクでログインし、設定画面でパスワードを変更する。**再設定専用の画面を作らずに済む。**

---

## 決定

### 認証方式

| 用途 | 方式 | 画面 |
| --- | --- | --- |
| **ログイン（主）** | メールアドレス + パスワード | `/login` |
| 新規登録 | メールアドレス + パスワード + **確認メール 1 通** | `/signup` |
| パスワードを忘れたとき | **マジックリンク**（ログインリンクをメールで送る） | `/login/link` |
| パスワードの変更 | ログイン後に設定画面から（M4） | `/settings` |

### 新規登録時のメール確認は有効にする

Supabase の「Confirm email」を ON のままにする（既定）。登録時に確認メールが 1 通届き、リンクを開くと有効化される。

- **所有していないメールアドレスで登録できない。** 招待コードを知らなければ世帯のデータは見られないが、他人のメールアドレスでアカウントを作られる状態にはしない
- 確認リンクもマジックリンクと同じ PKCE フローなので、**`/auth/callback` を共用できる**（追加実装なし）
- メールは登録時の 1 通だけ。以降のログインはパスワードのみ

### パスワードの要件

| 項目 | 値 |
| --- | --- |
| 最小長 | 8 文字 |
| 最大長 | 72 文字（bcrypt の上限） |
| 文字種の制約 | 設けない（長さだけを要求する） |
| 新規登録時の確認入力 | **あり**（打ち間違いで入れなくなるのを防ぐ） |

文字種を要求しないのは、複雑さの要求が実際には覚えにくいだけのパスワードを生む、という一般的な知見に従う。長さを優先する。

---

## 判断の理由

| 点 | 内容 |
| --- | --- |
| 実際に使う人の判断 | 開発者が自分で試したうえでの要望。推測より優先する |
| 毎日の摩擦が減る | セッションが切れてもメールを待たずに入れる |
| 家族への説明が簡単 | 「メールアドレスとパスワード」は説明が不要 |
| 追加作業が小さい | マジックリンクを残すので再設定画面が不要。`/auth/callback` も共用 |
| パスワード管理の負担 | パスワードマネージャに任せられる。`autoComplete` を正しく指定する |

## 結果

### 良くなること

- 2 回目以降のログインがメール往復なしで完了する
- 家族に説明しやすい
- マジックリンクが「パスワードを忘れたとき」の導線として活きる（捨てずに済む）

### 受け入れる代償

| 代償 | 対処 |
| --- | --- |
| **パスワードの総当たりを受けうる** | Supabase Auth の既定のレート制限に依る。v1 では自前の制限を作らない（利用者が家族のみ）。外部に公開するなら見直す |
| 弱いパスワードを設定されうる | 8 文字以上を要求する。文字種は要求しない |
| パスワードを忘れると一手間 | マジックリンクでログイン → `/settings` でパスワードを変更。**変更 UI は M2 の段階で用意した**（マジックリンクで作った既存アカウントにパスワードを設定する必要があったため） |
| **登録済みのアドレスで登録しても何も起きない** | Supabase は既存の確認済みアドレスに何も送らず成功を返す（存在を漏らさないため）。こちらも表示を変えないので、**待っても届かない状態になりうる**。`/signup` に「すでに登録済みの場合は届きません」という案内文を置いて緩和した |
| 画面が 1 つ増える（`/signup`） | 画面は 7 → 9（`/signup`, `/login/link`）。[UI/UX設計](../02-design/ui-ux-design.md) の「画面を増やさない」原則に対する例外として記録する |
| 登録時のメールは残る | 1 通だけ。これは所有確認のために受け入れる |

## 見直す条件

| 条件 | 対応 |
| --- | --- |
| パスワードの総当たりが観測された | レート制限、または段階的な遅延を追加する |
| 外部に公開する | 多要素認証とレート制限を必須にする |
| 家族がパスワードを忘れる頻度が高い | 再設定専用画面を作る（マジックリンク運用で足りなければ） |
| パスキーが家族の端末で普通に使えるようになった | パスキーの追加を検討する（パスワードは残す） |

---

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| マジックリンクのみ（元の設計） | 毎回のログインでメール往復が必要。実際に使って摩擦が分かった |
| パスワードのみ（マジックリンクを消す） | 再設定専用画面を作る必要が出る。マジックリンクは既に動いているので残すほうが安い |
| 新規登録のメール確認を無効にする | 所有していないメールアドレスで登録できてしまう。メールは登録時の 1 通だけなので、受け入れる |
| ソーシャルログイン（Google など） | OAuth の設定が増え、家族の Google アカウントに依存する（ADR-0001 の判断を維持） |
| パスワードに文字種の要求を課す | 覚えにくいだけのパスワードを生みやすい。長さを優先する |
