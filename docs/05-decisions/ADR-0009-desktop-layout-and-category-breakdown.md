## 背景

v1 が完成した（2026-11-08、M3 完了）。実際に使ってみた開発者から次の要望が出た。

> 画面の UI を変えていきたい。まず PC に関してはスマホと変えたい。
> ちゃんとサイドバーをつけたり、図を用いたりして見やすくしてほしい。

v1 は**スマホ中心**で設計し、PC は「最大幅 480px で中央寄せ」＝スマホの画面を
そのまま中央に置くだけだった（UI/UX設計 §8）。実装コストが最小で、
v1 の目的（記録が続くか確かめる）には十分だったが、PC では画面の
大半が余白になり、横幅を活かせていない。

### スコープの問題

**「図」は v1 で意図的に落とした項目**だった。

| プロダクト概要 §5.2 の記述 | 理由として書いていたこと |
| --- | --- |
| グラフ・カテゴリ別の内訳 | 合計が見えれば v1 の目的は満たせる |

**v1 が完成した今、この前提が変わった。** 「合計が見えれば足りる」は
記録が続くかを確かめる段階の判断で、記録が溜まり始めると
「今月どこに使ったか」が次の関心になる。

勝手に足さないルール（AGENTS.md「勝手に変えないこと」）に従い、
**本人に確認したうえで**この ADR で記録する。

### 確認した範囲

3 案を提示して選んでもらった。

| 案 | 内容 | 結果 |
| --- | --- | --- |
| **A** | **カテゴリ別の内訳だけ入れる** | **採用** |
| B | 内訳 ＋ 月次の推移（6 か月の棒グラフ） | 却下 |
| C | 図は入れず、レイアウトだけ直す | 却下 |

## 決定

### 1. PC は独立したレイアウトにする

| 画面幅 | ナビゲーション | 本文の幅 |
| --- | --- | --- |
| `md` 未満（スマホ） | **下部タブ**（変更なし） | 最大 480px |
| `md` 以上（PC・タブレット） | **左のサイドバー** | ホーム 最大 1152px（2 カラム）／設定 768px／フォーム 480px |

- **スマホの作りは変えない。** v1 で受入条件を通した構成をそのまま残す
- サイドバーはスマホには出さない（`md:flex`）。狭い画面では下部タブのほうが親指で届く
- 下部タブは PC には出さない（`md:hidden`）
- サイドバーには**世帯名と自分の表示名を常に出す**。家族と共有するアプリなので、「誰としてどの家計簿を見ているか」が常に見えている必要がある
- サイドバーの項目はスマホの下部タブより 1 つ多い（カテゴリの管理）。画面幅に余裕があるので設定の中に隠さない

**フォーム（`/new`・編集）は PC でも 480px のまま。** 横に広げると
視線の移動が増えて入力が遅くなる。この 2 画面は「速く終わらせる」ことが
最優先（NFR-U2）。

### 2. カテゴリ別の内訳を v1 に入れる（FR-L8）

当月の**支出**をカテゴリ別に、金額・割合・横棒で出す。

| 事項 | 決定 |
| --- | --- |
| 対象 | **支出のみ**。収入は件数が少なく内訳を見る動機が薄い |
| 並び | 金額の多い順。同額なら名前の読み順（表示が毎回入れ替わらないように） |
| 表示する画面 | **ホームの PC 表示のみ。** スマホには出さない |
| 形 | **横棒。** 円グラフにしない |
| 期間 | 表示中の月だけ。月次の推移は入れない（案 B を却下） |

#### なぜ円グラフにしないか

- スマホ幅で凡例を置く場所が無い
- 扇形の面積から値を読み取るのは難しい（人間は角度の比較が苦手）
- 横棒なら**名前・金額・割合を同じ行に並べられる**

#### なぜスマホには出さないか

カテゴリが 13 個あると縦に伸び、**一覧（この画面の主役）が下に押し出される。**
スマホの画面は「今月いくら使ったか」と「直近の記録」を見るためのもの。
必要になったら別画面として足す（v2）。

#### なぜグラフのライブラリを入れないか

横棒は `div` 2 つと `width: %` で描ける。recharts（週間 6,459 万 DL、
2026-11-03 更新）は十分に信頼できるが、**この用途には要らない。**
依存を 1 つ増やすと、更新の追従とバンドルサイズを永続的に抱える（NFR-M7）。

ツールチップ・ズーム・軸ラベルといった対話機能が必要になったら、その時点で
改めて ADR を書いて導入する。

### 3. 集計は DB に問い合わせない

`breakdownByCategory(rows)` は**純関数**で、ホーム画面が既に取得している
行から計算する。

**集計用のクエリを足さない理由は認可。** DAL に関数を 1 つ足すと、
`householdId` の条件を書き忘れうる場所が 1 つ増える
（[ADR-0005](./ADR-0005-authorization-in-app-layer.md) の約束 B）。
既に認可を通った行を使えば、その面が増えない。

| | 新しい DAL 関数を足す | 既存の行から計算する（採用） |
| --- | --- | --- |
| クエリ数 | +1 | 変わらない |
| 認可を書き忘れうる場所 | +1 | 増えない |
| 必要なテスト | 認可テスト（DB 必須） | 純関数のテスト（DB 不要、速い） |

### コントラストで 2 件落ちた

`--chart-*` はこれまで使っていなかったので未検査だった。検査に加えたところ、
**ライトの `chart-4` が 2.67:1、ダークの `chart-1` が 2.95:1** で基準（3:1）を
下回っていた。明度を調整して両方 3:1 以上にした。

棒自体は装飾（金額と割合を文字でも出している）だが、**下地と区別できないと
「どこまで伸びているか」が読めない**ので非テキストの基準を課している。

## 見直す条件

| 条件 | 対応 |
| --- | --- |
| スマホでも内訳を見たくなった | 別画面（`/breakdown`）として足す。ホームに積まない |
| 月次の推移が見たくなった | 案 B を改めて検討する。推移は過去 6 か月ぶんのクエリが必要で、DAL 関数の追加（＝認可テストの追加）を伴う |
| 対話的なグラフが必要になった | recharts の導入を ADR で検討する |
| タブレットで下部タブのほうが使いやすいと分かった | 境界を `md` から `lg` に上げる |

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| **案 B（内訳 ＋ 月次の推移）** | 推移は DAL 関数の追加（＝認可の面の追加）を伴い、v1 からの逸脱が大きい。**まず内訳が実際に役立つか見てから判断する** |
| **案 C（図を入れない）** | 本人の要望が「図を用いて見やすく」だった。レイアウトだけでは応えていない |
| 円グラフ | 値を読み取りにくく、スマホ幅で凡例の場所が無い |
| recharts を入れる | 横棒だけなら `div` で足りる。依存の維持コストに見合わない（NFR-M7） |
| スマホにも内訳を出す | カテゴリ 13 個で縦に伸び、一覧が下に押し出される |
| サイドバーをスマホでも開閉式（ドロワー）にする | 下部タブが既にあり、導線が二重になる。v1 の構成を壊さない |
| PC でもフォームを横に広げる | 視線の移動が増えて入力が遅くなる。`/new` は速さが最優先（NFR-U2） |
