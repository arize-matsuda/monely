# ADR-0013: メール確認を必須にしない（独自ドメインを持たない前提）

| | |
| --- | --- |
| **状態** | 採用（Accepted） |
| **日付** | 2026-11-09 |
| **決定者** | 開発者本人 |
| **置き換える** | [ADR-0006](./ADR-0006-email-password-auth.md) の「新規登録時にメール確認を必須にする」という判断 |
| **維持する** | [ADR-0006](./ADR-0006-email-password-auth.md) のメール + パスワード認証、[ADR-0007](./ADR-0007-better-auth.md)（better-auth）、[ADR-0005](./ADR-0005-authorization-in-app-layer.md)（約束 A/B/C） |

## 背景

本番にデプロイしたあと、本人がアカウントを作ろうとして**確認メールが
届かなかった**（2026-11-09）。

本番 DB を見ると `user` は作られていて `emailVerified = false`、
`verification` は 0 件。**登録処理は動いていて、送信だけが行われていなかった。**
原因は `RESEND_API_KEY` / `MAIL_FROM` の未設定。

### メールを送るには独自ドメインが要る

| 送信元 | 宛先 | 独自ドメイン |
| --- | --- | --- |
| Resend の検証済みドメイン | **任意** | **必要** |
| Resend のテスト送信元（`onboarding@resend.dev`） | **Resend アカウントのアドレスだけ** | 不要 |

**家族を招待するには任意の宛先に送れる必要がある**ため、Resend では
独自ドメインが必須になる。

### 提示した選択肢

| 案 | 内容 | 失うもの |
| --- | --- | --- |
| **A** | **メール確認を必須から外す** | **パスワードの再設定** |
| B | `nodemailer` で Gmail の SMTP を使う（独自ドメイン不要、任意の宛先に送れる） | なし（依存 1 つ増える） |
| C | 単一送信元の検証ができる他社に替える | 要調査 |

**B を勧めた**（パスワード再設定を失わずに済むため）。本人の選択は
**A「一番簡単だから」**。独自ドメインは設定しない方針も明言された。

---

## 決定

### `requireEmailVerification: false` にする

```ts
// src/lib/auth/server.ts
emailAndPassword: {
  enabled: true,
  requireEmailVerification: false,
  …
}
```

**メール送信の設定自体は残す。** `RESEND_API_KEY` と `MAIL_FROM` を
入れた環境では確認リンクを送る。届く環境では従来どおり確認してもらえる。

### データの安全性は変わらない

| | |
| --- | --- |
| 認可の入口 | **招待コード**（6 桁。世帯の全データへのアクセス権と同等に扱う。BR-9） |
| 世帯に未所属のアカウント | `requireMember()` が `/setup` に送る。**記録は 1 件も見えない** |
| アプリ側の `emailVerified` 参照 | **無い**（`grep` で確認済み）。認可の判断に使っていない |

メール確認は「そのアドレスの所有者である証明」であって、
**このアプリの認可には一度も使っていなかった。**
[ADR-0005](./ADR-0005-authorization-in-app-layer.md) のとおり、
認可は `src/lib/data/` の `where` 句だけが担う。

### 失うもの: パスワードの再設定

**これが A の唯一かつ重大な代償。**

| 経路 | 状態 |
| --- | --- |
| マジックリンク（FR-A6） | メール送信に依存するため**使えない** |
| パスワード再設定 | 同じく**使えない** |
| ログイン中の変更（`/settings`） | **使える**（メール不要） |

**ログアウトした状態でパスワードを忘れると、自力では戻れない。**
本人にこの点を明示したうえでの選択。パスワードは利用者が保管する前提。

詰まった場合の復旧は DB 操作（`account` テーブルのパスワードハッシュの
差し替え、または `emailVerified` を立ててマジックリンクを使う）に限られる。

### 行き止まりのリンクを隠す

メールが送れない環境では、`/login` から次の 2 つを出さない。

- 「ログインリンクを受け取る」
- 「確認メールを再送する」

**出すと「送りました」と表示されるのに届かない。** 代わりに
「いまメールを送信できない設定のため、パスワードの再設定はできません」と
事実を書く。`isMailConfigured()` で判定するので、設定すれば自動で戻る
（ビルド時の判定なので再デプロイが要る）。

### 新しく生まれるリスク

**他人のメールアドレスで登録できる**（所有証明がなくなるため）。

ただし得られるのは**空のアカウント**だけで、記録は見えない。
実害は「そのアドレスの本来の持ち主が、同じアドレスで登録できなくなる」
こと。利用者が 2 人の招待制アプリ（[project-overview §5.3](../00-overview/project-overview.md)）では
受け入れられる範囲と判断した。

## 見直す条件

| 条件 | 対応 |
| --- | --- |
| **パスワードを忘れて入れなくなった** | DB 操作で復旧する。そのうえで案 B（Gmail SMTP）の導入を再検討する |
| 独自ドメインを用意した | `RESEND_API_KEY` / `MAIL_FROM` を設定する。**コードの変更は不要**（確認リンクが自動で送られ、リンクも自動で出る）。`requireEmailVerification` を `true` に戻すかは別途判断 |
| 家族以外にも使わせたくなった | **メール確認を戻す。** 所有証明が無い状態で公開してはいけない |
| 登録を招待コードの所持者だけに絞りたくなった | 新規登録の時点で招待コードを要求する形に変える（いまは登録は誰でもでき、世帯の参加だけが招待コードで守られている） |

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| **案 B（Gmail SMTP + nodemailer）** | **勧めたが選ばれなかった。** 本人の判断は「一番簡単だから A」。依存 1 つとアプリパスワードの設定が要る |
| 案 C（単一送信元の検証ができる他社） | 各社の現在の仕様を確認していないため、断言できなかった |
| 独自ドメインを取る | 本人が「設定しないつもり」と明言 |
| Resend のテスト送信元で運用する | **宛先が Resend アカウントのアドレスだけ。** 家族を招待できない |
| メール機能を完全に削除する | 独自ドメインを用意したら戻せる形にしておきたい。**設定するだけで動く**状態を保つ |
| 新規登録に招待コードを要求する | 招待制を本当に強制できるが、流れが変わり「一番簡単」から離れる。見直す条件に残した |
