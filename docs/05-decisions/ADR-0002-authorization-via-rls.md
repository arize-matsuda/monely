## 背景

Monely は家族で 1 つの家計簿を共有する。つまり **DB に複数の世帯のデータが同居し、世帯の境界を越えて見えてはならない**。家計のデータは金額と生活のパターンが分かる個人情報で、漏れたときの影響は小さくない。

認可の実装場所には複数の選択肢がある。

| 置き場所 | 具体例 |
| --- | --- |
| アプリのクエリ | `.eq("household_id", me.householdId)` を毎回書く |
| アプリの共通層 | リポジトリ層やミドルウェアで世帯 ID を自動付与する |
| DB | PostgreSQL の RLS（行レベルセキュリティ） |

制約として、**開発者は 1 人でレビュアーがいない**。「書き忘れ」を人の注意力やレビューで防ぐ設計にできない。画面とアクションは今後増える。

---

## 決定

**認可の本体を PostgreSQL の RLS に置く。**

1. `households` / `profiles` / `categories` / `transactions` の 4 テーブルすべてで RLS を有効にする。
2. 「自分の世帯の行だけ」を `household_id = public.current_household_id()` の条件で表現する。
3. `current_household_id()` は `security definer` 関数とし、`auth.uid()` のみを見る（引数を取らない）。
4. **アプリのクエリに書く `household_id` の条件は、取得量を絞るためのものであってセキュリティではない。**
5. **`service_role` キーをアプリに持ち込まない。** このキーは RLS を完全にバイパスするため、使えばこの決定が無意味になる。
6. RLS で表現できない複合操作（世帯の作成・参加）は `security definer` の RPC に閉じ込める。

```sql
create policy transactions_select on public.transactions
  for select to authenticated
  using (household_id = public.current_household_id());
```

## 判断の理由

### 1. 書き忘れが漏洩にならない

アプリのクエリに条件を書く方式では、**1 箇所の書き忘れがそのまま漏洩になる**。画面が 7 つ、読み取り関数が 5 本、アクションが 10 本程度でも、変更のたびに全箇所を見直す必要がある。

RLS なら、アプリが条件を書き忘れても DB が行を返さない。守りの箇所が 1 層に固定され、画面が増えても守り方が変わらない。

### 2. レビュアーがいない

1 人開発では「別の目で見る」工程が存在しない。**人の注意力に依存しない構造**を選ぶ必要がある。RLS は「ポリシーを書き忘れたテーブルは誰も読めない」という安全側の失敗をする。

### 3. 共通層による自動付与では足りない

リポジトリ層で世帯 ID を自動付与する方式は、その層を通らない経路（新しく書いたクエリ、デバッグ用のコード、将来の管理機能）が抜け穴になる。**層を迂回できることが構造的な弱点。** DB は迂回できない。

### 4. 多層防御の最下層として機能する

RLS を置いても、アプリ側の検証は不要にならない。両者は役割が違う。

| 層 | 防げるもの | 防げないもの |
| --- | --- | --- |
| アプリ（Server Action 内の検証） | 他世帯の `category_id` / `paid_by` の紐付け | 検証の書き忘れ |
| RLS | 他世帯の行の読み書き | 参照先の所属の不整合 |

**どちらも必要。** 詳細 → [セキュリティガイドライン §4.4](../03-guidelines/security-guidelines.md#44-参照先の所属も確認する)（この論点は ADR-0005 でも引き継がれている）

## 結果

### 良くなること

- 守りの箇所が DB の 1 層に固定される。画面やアクションが増えても守り方が変わらない。
- 書き忘れが漏洩にならない。
- 検証手順が固定できる（2 アカウントでの侵入確認、または SQL でのセッション模倣）。
- SQL Editor から手で触るときも同じ保護がかかる（`service_role` を使わない限り）。

### 受け入れる代償

| 代償 | 対処 |
| --- | --- |
| RLS の学習コスト | DB設計（当時の §5。現在の版には RLS の節は無い） に書き方と注意点を記録 |
| `profiles` のポリシーが自己参照して無限再帰する罠 | `current_household_id()` を `security definer` にする。理由を DB設計（当時の §4.1） に明記 |
| `security definer` 関数自体が穴になりうる | `set search_path = public` を必須にし、ID を引数で受け取らない設計を規約化 |
| ポリシーの誤りがテストでは見つからない | [RLS の侵入確認](../03-guidelines/testing-strategy.md#42-認可の確認毎回実施)を M2 以降**毎回**実施する |
| ORM が使いにくくなる | ORM を使わない（[ADR-0001](./ADR-0001-tech-stack.md)） |
| 管理操作（全世帯を見る等）ができない | 必要なら Supabase ダッシュボードの SQL Editor で手で実行する。アプリに管理機能を作らない |

## 守らなければならない前提

この決定は、以下が守られて初めて意味を持つ。**1 つでも破れば無効になる。**

- [ ] `service_role` キーをアプリで使わない（`grep -rn "service_role" src/` が 0 件）
- [ ] 新しいテーブルを作ったら、その場で RLS を有効にする
- [ ] ポリシーに `to authenticated` を付ける（`anon` に開かない）
- [ ] UPDATE のポリシーに `using` と `with check` を両方書く
- [ ] `security definer` 関数に `set search_path = public` を付ける
- [ ] `security definer` 関数が ID を引数で受け取らない
- [ ] テーブルや列を足したら侵入確認を再実行する

チェックリスト → [セキュリティガイドライン §10](../03-guidelines/security-guidelines.md#10-実装後のチェックリスト)

## 見直す条件

| 条件 | 見直す対象 |
| --- | --- |
| Supabase から別の DB へ移る | 移行先が RLS 相当の機能を持つか。持たなければ認可の置き場所を再検討 |
| 管理者向けの機能が必要になる | `service_role` を使わずに実現する方法（専用の RPC など）を先に検討 |
| 1 人が複数世帯を扱う必要が出る | `current_household_id()` を「選択中の世帯」を返す実装に差し替える（→ [ADR-0003](./ADR-0003-one-household-per-user.md)） |
| 権限の分離（閲覧専用メンバー）が必要になる | ポリシーに役割の条件を足す |

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| アプリのクエリに毎回 `household_id` の条件を書く | 1 箇所の書き忘れが漏洩になる。レビュアーがいない体制で選べない |
| リポジトリ層で世帯 ID を自動付与する | 層を迂回できることが構造的な弱点 |
| `service_role` キーでアクセスし、アプリ側だけで制御する | RLS をバイパスする。最も危険な選択 |
| Firestore のセキュリティルール | DB 自体の選定の話（→ [ADR-0001](./ADR-0001-tech-stack.md)）。SQL と RLS の方が家計簿のデータ構造に合う |
