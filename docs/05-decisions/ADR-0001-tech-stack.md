## 背景

家計管理アプリ Monely を自作する。制約は次の通り。

| 制約 | 内容 |
| --- | --- |
| 開発者 | 1 人。レビュアーはいない |
| 利用者 | 自分 + 家族（数人） |
| 端末 | スマホ中心。PWA としてホーム画面に追加したい |
| 共有 | 家族が同じデータを見る。**認証と権限分離が必須** |
| 費用 | 無料〜低額に収めたい |
| 保守 | 長く使う。依存の更新が止まったものに乗りたくない |
| 現状 | リポジトリは `create-next-app` 直後の状態（Next.js 16.4.5 + React 19 + Tailwind v4 + Biome + pnpm） |

**家族で共有する以上、「他人のデータが見えない」ことを設計の中心に置く必要がある。** これが選定の最大の軸。

## 決定

| 層 | 採用 | バージョン |
| --- | --- | --- |
| フレームワーク | **Next.js（App Router）** | 16.4.5 |
| UI | React + Tailwind CSS | 19.3.0 / v4 |
| DB・認証 | **Supabase**（PostgreSQL + Supabase Auth） | クラウド無料プラン |
| DB アクセス | `@supabase/supabase-js` + `@supabase/ssr`（ORM なし） | 2.119.0 / 0.12.7 |
| 認可 | **PostgreSQL の RLS（行レベルセキュリティ）** | — |
| API 層 | **作らない**（Server Actions + Server Components） | — |
| 認証方式 | メールのマジックリンク（パスワードなし） | — |
| Lint / Format | Biome のみ | 2.4.2 |
| パッケージ管理 | pnpm | 12.18.0 |
| テスト | **v1 では導入しない**（手動の受入確認） | — |
| デプロイ先 | **未定**（まずローカルで完成させる） | — |

## 判断の理由

### 1. Next.js（App Router）

- リポジトリが既に `create-next-app` で作られている。乗り換えるコストに見合う理由がない。
- Server Components と Server Actions により、**DB アクセスをサーバー側に閉じ込めたまま 1 つのコードベースで完結する**。別のバックエンドを立てなくてよい。
- PWA に必要な manifest をフレームワークが扱える。
- **代償**: 16.4.5 は新しく、`cacheComponents` や `proxy.ts`（旧 Middleware）など一般的な記事と差がある。`node_modules/next/dist/docs/` の同梱ドキュメントを一次情報とする運用でこれを吸収する。

### 2. Supabase

家族共有に必要な「認証 + 権限分離された DB」を、自分で作らずに得られる。

| 検討した代替 | 却下の理由 |
| --- | --- |
| ローカル完結（IndexedDB） | **家族共有ができない。** 要件を満たせない |
| SQLite + 自前の認証 | 認証の自作は事故の確率が高い。マジックリンクのメール送信も自前では面倒 |
| Firebase | Firestore のセキュリティルールより、**SQL と RLS の方が家計簿のデータ構造に合う**。集計も SQL で書ける |
| PlanetScale / Neon + Auth.js | 認証とメール送信を別に組み合わせる手間。Supabase は 1 つで揃う |

**無料プランの範囲**: 利用者数人、データ 15,000 行程度で、制限に当たらない。

### 3. 認可を RLS に置く

**この決定が最も重要。** アプリのクエリに条件を書き忘れても他世帯のデータが漏れないことを、DB の保証として持つ。1 人開発でレビュアーがいないため、「書き忘れ」を人の注意力で防ぐ設計にできない。

→ 独立した判断として [ADR-0002 認可を PostgreSQL の RLS に置く](./ADR-0002-authorization-via-rls.md) に記録した。

### 4. ORM を使わない

| 検討した代替 | 却下の理由 |
| --- | --- |
| Prisma | RLS を効かせるには接続ユーザーの JWT を引き回す必要があり、Supabase クライアント経由より手間が増える |
| Drizzle | 同様。加えてスキーマの正が 2 箇所（SQL とスキーマ定義）になる |

スキーマの正を `supabase/migrations/*.sql` の 1 箇所に置き、`@supabase/supabase-js` で素直に読み書きする。テーブルが 4 つなので、型の自動生成がなくても手書きの型で足りる。

### 5. API 層を作らない

クライアントは同じ Next.js アプリだけ。HTTP の API 層を作ると、型定義・検証・エラー処理が二重になる。

- 読み取り → Server Component から直接
- 変更 → Server Action
- 認証コールバックのみ Route Handler（ブラウザからの GET が必要なため）

**代償**: 将来ネイティブアプリを作る場合は API 層が必要になる。その時点で検討する（今は必要になる見込みが低い）。

### 6. マジックリンク認証

| 検討した代替 | 却下の理由 |
| --- | --- |
| メール + パスワード | **家族にパスワードを管理させたくない**（課題 B-2）。リセットのフローも作る必要がある |
| Google ログイン | OAuth の設定が増える。家族の Google アカウントに依存する |
| パスキー | 対応端末・ブラウザの前提が増える。利用者 2〜3 人で冒険しない |

Supabase Auth の標準機能だけで完結し、外部サービスの設定が不要。**代償**: メールが届かない・リンクが期限切れになる、メールクライアントの先読みでコードが消費される、といった問題が起きうる。失敗時に「もう一度送る」導線を必ず置く。

### 7. Biome のみ（ESLint / Prettier を入れない）

スキャフォールドに既に入っており、Lint と Format が 1 つのツールで済む。設定ファイルが 1 つで、依存が少ない。

### 8. テストフレームワークを v1 で入れない

画面が 7 つ、純粋なロジックが数本の規模。**使われないテストは腐り、腐ったテストは無いより悪い。**

代わりに、受入条件（AC-1〜AC-12）を手で確認する手順を [テスト戦略](../03-guidelines/testing-strategy.md) に固定する。導入条件も同文書に明記した（ロジックが 3 本以上に増えたら Vitest、など）。

**代償**: 回帰に気づけない。特に金額・日付の計算と RLS は影響が大きいため、毎回手で確認する項目として指定した。

### 9. デプロイ先を今決めない

ローカルで完成させるまで必要にならない。PWA の検証（M5）の直前に決める。

- Next.js なので Vercel が最短。無料枠で足りる。
- ただし今決めると、不要な設定作業が先に入る。

## 結果

### 良くなること

- 家族共有・認証・権限分離が、自作コードをほとんど書かずに成立する。
- 守りの箇所が DB の 1 層に固定され、画面が増えても守り方が変わらない。
- 依存が 5 つ（`next`, `react`, `react-dom`, `@supabase/supabase-js`, `@supabase/ssr`）で、更新の追従が軽い。
- 費用が無料枠に収まる。

### 受け入れる代償

| 代償 | 対処 |
| --- | --- |
| Supabase への依存（サービス終了・料金変更のリスク） | データは PostgreSQL。標準的な SQL で他へ移せる。ORM を挟まない分、移行先の選択肢も狭まらない |
| Next.js 16 の情報が少ない | 同梱ドキュメントを一次情報とする運用を [コーディング規約 §5.4](../03-guidelines/coding-standards.md#54-nextjs-16-固有) に明記。`cacheComponents` への対応は [ADR-0004](./ADR-0004-instant-false-for-authed-segments.md) |
| RLS の学習コスト | [ADR-0002](./ADR-0002-authorization-via-rls.md) と [DB設計](../02-design/database-design.md) に設計意図と罠を記録。[テスト戦略](../03-guidelines/testing-strategy.md#42-認可の確認毎回実施) に検証手順を固定 |
| 自動テストがない | 受入条件を手順化。導入条件を明記 |
| ローカル開発でも本番 DB に接続する | 確認で入れたデータを後で消す運用（NFR-O3）。環境分離は v2 で検討 |
| 複数世帯に所属できない | v1 の要件外。中間テーブルの追加で移行可能な設計にした（→ [ADR-0003](./ADR-0003-one-household-per-user.md)） |

## 見直す条件

以下のいずれかが起きたら、この ADR を新しい番号の ADR で置き換える。**この文書は書き換えない。**

| 条件 | 見直す対象 |
| --- | --- |
| ネイティブアプリを作る | API 層の追加 |
| 自分以外が開発に入る | テストフレームワーク、環境分離、CI |
| 利用者が世帯外に広がる | 認証方式、レート制限、監査ログ |
| Supabase の無料枠を超える | DB の移行先、または有料プラン |
| 1 人が複数世帯を扱う必要が出る | データモデル（→ [ADR-0003](./ADR-0003-one-household-per-user.md)） |
| オフラインで記録したい要求が出る | ローカル保存 + 同期の仕組み |
| 画面遷移が体感で遅い | レンダリング方針（→ [ADR-0004](./ADR-0004-instant-false-for-authed-segments.md)） |

## 却下した選択肢（まとめ）

| 選択肢 | 却下の理由 |
| --- | --- |
| ローカル完結（IndexedDB のみ） | 家族共有ができない |
| Firebase / Firestore | 家計簿のデータ構造と集計に SQL の方が合う |
| 自前の認証実装 | 事故の確率が高い |
| ORM（Prisma / Drizzle） | RLS との相性、スキーマの正が二重化する |
| REST / GraphQL の API 層 | クライアントが 1 つなので二重の手間 |
| 状態管理ライブラリ | サーバーからの props と `useState` で足りる |
| UI コンポーネントライブラリ | 画面が 7 つ。依存を増やす価値が薄い |
| 検証ライブラリ（zod 等） | 項目数が少なく、手書きの関数で足りる |
| テストフレームワーク（v1） | 規模に対して保守コストが上回る |
