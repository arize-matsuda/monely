## 背景

[ADR-0006](./ADR-0006-email-password-auth.md) でメール + パスワード認証に切り替え、Supabase Auth の上に実装した。開発者から「認証を自前でやりたい」という要望があり、まず Auth.js が候補に挙がった。

### 調査した事実（2026-11-08、npm の実データ）

| ライブラリ | 週間DL | 最新版 | 最終更新 |
| --- | --- | --- | --- |
| **better-auth** | 18,714,403 | 1.7.18（安定） | 2026-11-05 |
| next-auth / Auth.js | 9,403,576 | 4.24.15（安定）/ **5 は beta のみ** | 2026-07-20 |
| @clerk/nextjs | 3,749,727 | 7.9.25 | 2026-11-07 |
| lucia | 694,830 | **非推奨（deprecated）** | 2025-06 |

- **Auth.js の v5 は 2023-10-24 から 33 リリース、3 年以上 beta のまま安定版が無い。** 本体も約 4 か月更新が止まっている
- Auth.js は**メール + パスワード（Credentials provider）を公式に非推奨**としており、今回の用途と噛み合わない
- better-auth は `prisma ^5 || ^6 || ^7` と `@prisma/client ^5 || ^6 || ^7` を peer deps で名指しサポート（このプロジェクトは Prisma 7.10.1）
- better-auth はメール + パスワード・メール確認・パスワード再設定・マジックリンクが標準機能

### 今日詰まった問題はこの移行では解決しない

| 起きたこと | 原因 | 移行で解決するか |
| --- | --- | --- |
| 登録してもメールが来ない | 既存アカウントの存在を隠す仕様 | **しない**（自前でも同じ判断が必要） |
| メールの送信制限に達した | Supabase の組み込み SMTP | **しない**（自前でもメール送信手段が必要） |

これは開発者にも伝えたうえでの判断。**移行の動機は「今日の不便の解消」ではなく、構成の一貫性と依存の縮小。**

---

## 決定

**Auth.js ではなく better-auth を採用し、認証を Prisma 側に寄せる。**

| | 変更前 | 変更後 |
| --- | --- | --- |
| 認証の実装 | Supabase Auth（GoTrue） | **better-auth 1.7.18** |
| ユーザーの保存先 | `auth.users`（Supabase 所有、Prisma 管理外） | **`user` / `session` / `account` / `verification`（Prisma 管理）** |
| セッション | JWT + リフレッシュトークン（Cookie） | **DB セッション**（`session` テーブル + Cookie） |
| トークンの検証 | 毎リクエスト Supabase に HTTP 問い合わせ | **DB の 1 クエリ**（同じ Postgres） |
| メール送信 | Supabase の組み込み SMTP | **自前**（`src/lib/email.ts`） |
| Supabase の役割 | DB + 認証 | **DB のみ**（ただの Postgres） |
| 認証方式 | メール + パスワード、マジックリンクは再設定用 | **変更なし**（ADR-0006 を維持） |

### Auth.js を却下した理由

指定されたのは Auth.js だったが、**3 年以上 beta のまま安定版が無く、メール + パスワードを公式に非推奨としている**ライブラリを認証基盤に置くのは、長く使うアプリとして勧められない。開発者に事実を提示したうえで better-auth を選んだ。

### メール送信を自前で用意する

better-auth は**メールを送らない**（送信関数を渡す設計）。そのため `src/lib/email.ts` を作る。

| 条件 | 動作 |
| --- | --- |
| `RESEND_API_KEY` がある | Resend の REST API に `fetch` で送信（**パッケージを追加しない**） |
| 鍵が無い（開発時） | **コンソールにリンクを出力する** |

開発時にコンソールへ出す形にしたのは、**メールの往復と送信制限を待たずにテストできる**から。今日はこれで何度も詰まった。

---

## 得られるもの

| 点 | 内容 |
| --- | --- |
| スキーマが 1 箇所に集まる | `auth` スキーマが Prisma 管理外である状態が解消。`Profile.userId` に**本物の外部キー**を張れる |
| Supabase から抜けやすくなる | Supabase が「ただの Postgres」になる。移行先の選択肢が広がる |
| HTTP 往復が消える | ページ表示ごとの Supabase への問い合わせが、同じ DB への 1 クエリになる |
| メールの制限から解放される | 送信手段を自分で選べる。開発時はコンソールで完結 |
| 依存が減る | `@supabase/supabase-js` と `@supabase/ssr` を削除（`better-auth` を 1 つ追加） |

## 受け入れる代償

| 代償 | 対処 |
| --- | --- |
| **認証の実装責任がライブラリに移る** | 暗号処理は better-auth が行うので「自作」ではない。ただし Supabase のマネージドな保護（レート制限など）は失う |
| **レート制限を自分で考える必要がある** | better-auth の `rateLimit` オプションを有効にする。v1 では既定値 + メール送信の抑制に留める |
| セッションが DB に乗る | `session` テーブルが増える。利用者が数人なので問題にならない |
| **既存データを捨てる** | 取引 0 件の段階なので実害なし。詳細は下記 |
| メール送信の設定が必要 | `RESEND_API_KEY` を入れるまでコンソール出力。家族を招待する前に設定する |
| 移行の手戻り | ADR-0006 で作った画面は**そのまま使える**（フォームとアクションの中身だけ差し替え） |

### 既存データの扱い

移行時点の状態: ユーザー 1 名、世帯 1 件、カテゴリ 18 件、**取引 0 件**。

`Profile.userId` の型が変わる（`uuid` → `text`。better-auth の ID は UUID ではない）ため、**アプリのデータを空にしてから移行する**。取引が 0 件で、世帯は `/setup` で 30 秒で作り直せるので、移行スクリプトを書く価値がない。

マイグレーション `0003_better_auth` で明示的に削除する。**この判断は取引データが存在する前にしか取れない。**

## 見直す条件

| 条件 | 対応 |
| --- | --- |
| better-auth の更新が止まった | 週間DL と最終更新を確認し、移行先を再検討する |
| 総当たりや不審なログインが観測された | `rateLimit` を強化し、ログインの失敗回数の制限を追加する |
| 家族以外に公開する | 多要素認証（`two-factor` プラグイン）とレート制限を必須にする |
| セッションの DB 負荷が問題になった | `session.cookieCache` を有効にする |

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| **Auth.js（指定された案）** | v5 が 3 年以上 beta で安定版が無い。メール + パスワードを公式に非推奨。本体の更新も停滞 |
| Supabase Auth のまま + カスタム SMTP | 今日の不便は解消するが、`auth` スキーマが Prisma 管理外である状態と HTTP 往復は残る。開発者は構成の一貫性を選んだ |
| Clerk / Auth0 などのマネージド | Supabase Auth から乗り換える理由が薄い。無料枠を超えると課金 |
| lucia | 公式に非推奨（移行先として better-auth が案内されている） |
| 既存ユーザーのパスワードハッシュを移行する | better-auth の既定は scrypt、Supabase は bcrypt。ハッシュ方式を合わせる設定を入れるより、1 名なので再登録するほうが単純 |
