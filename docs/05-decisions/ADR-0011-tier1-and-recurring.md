## 背景

v1 が完成し、PC レイアウト・先月比・年のページまで入ったところで、
本人から「このような機能があればいいなというモノを教えてほしい」と
依頼があった。調査のうえ 3 段階で提案し、**「Tier 3 まで実装してほしい。
そこから実際に使っていきたい」**という回答を得た。

### 提案の根拠にした事実

| 事実 | 出どころ |
| --- | --- |
| **`paidById` を v1 から記録しているのに、一覧に名前を出すだけで一度も集計していない** | `grep` で全参照を確認 |
| `createdById` は保存しているが画面に一切出していない（FR-T9 のとおり意図的） | 同上 |
| 先月ぶんの行はホームが先月比（FR-L9）のために既に取得している | `src/app/(app)/page.tsx` |
| 予算・定期支出は [プロダクト要件](../01-requirements/product-requirements.md) §5 の v2 候補の 2 位・3 位 | 既存ドキュメント |
| 検索・口座残高・レシート取り込みは §5.2 で意図的に落としている | 同上 |

### 提案しなかったもの

一般公開・広告は §5.3「将来もやらないと決めたこと」なので候補に入れていない。
口座・資産残高、レシート撮影、銀行連携は §5.2 の判断を維持した。

## 決定

### Tier 1: 既にあるデータだけで作る（DB 変更なし）

**3 つとも純関数 + 表示だけ。DAL 関数も認可の面も増やしていない**
（[ADR-0009](./ADR-0009-desktop-layout-and-category-breakdown.md) §4 と同じ方針）。

#### FR-T11 記録の複製

編集画面に「これと同じ記録を作る」。`/new?amount=&category=&paidBy=&memo=&kind=`
で初期値を渡す。

| 事項 | 決定 |
| --- | --- |
| **日付は引き継がない** | 複製の用途は「毎月同じものを今月も入れる」。日付は常に今日が正しい |
| URL の値 | **選択肢に無いカテゴリ / メンバー ID は捨てる。** 存在しない ID を「選択済み」に見せないため。保存の可否は従来どおり DAL が判断する（約束 B） |
| 金額 | 全角とカンマを許容。数字以外・上限超えは空にする（弾くのではなく無視する） |

#### FR-L11 記録忘れの提示

先月にあって今月まだ無い支出カテゴリを「入れ忘れ？」として出す。
家賃・通信・サブスクは**入れ忘れても何も表示されないので気づけない。**

| 事項 | 決定 |
| --- | --- |
| 出す条件 | **今月を見ているときだけ。** 終わった月に出しても意味が無い |
| データ | **追加クエリ 0。** 先月ぶんは先月比のために取得済み |
| 未分類 | 候補にしない（「何を入れ忘れたか」が伝わらない） |
| 導線 | 先月の金額つきで `/new` へ（FR-T11 と接続） |

#### FR-L12 支払者別の集計と精算

| 事項 | 決定 |
| --- | --- |
| 出す条件 | **メンバーが 2 人以上**かつ支出がある月 |
| 払っていないメンバー | **0 円で並べる**（誰が払っていないかが分かる） |
| 精算額を出す条件 | **2 人の世帯**かつ**支払者が全員分かっている**とき |
| 精算の方法 | 均等割り。差額の半分を多く払った人へ。1 円未満は切り捨て |

精算額を絞った理由:

- 支払者が未指定の行があると「誰が払ったか」が確定しない
- **3 人以上は組み合わせが増え、収入比など別の分担も考えたくなる。** v1 の範囲を超える

家計を完全に合算している場合は、精算額を無視して支払者別の金額だけ見ればよい。

### Tier 2: 予算（FR-B1〜B3）— テーブル追加

内訳で「食費 42%」は見えるようになったが、**それが使いすぎなのか
分からない。** 予算は「数字を見る」から「行動が変わる」に進む一手。

| 事項 | 決定 |
| --- | --- |
| テーブル | `budgets(household_id, category_id, amount)`。一意制約は `(household_id, category_id)` |
| **月ごとの予算は持たない** | 毎月同じ額が適用される。月ごとに変えたくなったら `(household_id, category_id, month)` に広げる |
| 0 円の扱い | **行を消す。** 削除の操作を別に用意すると画面にボタンが増える |
| 設定画面 | `/settings/budgets`。**1 つのフォームで全カテゴリをまとめて保存**（1 件ずつだと 13 回の送信になる） |
| 対象 | **支出のカテゴリだけ。** 収入に予算を立てる動機が無い |
| 消化率の表示 | カテゴリ別の内訳の棒を**「予算に対する消化率」に差し替える**（支出全体の割合より行動に繋がる） |
| 超過の表示 | **`--destructive` を使う** |
| 予算外の支出 | 合計の消化率に**含めない**（混ぜると「使いすぎ」と「予算外の支出」が区別できない） |

#### 超過に赤を使う理由

「支出を赤にしない」という既存の方針（UI/UX設計 §6.3）とは矛盾しない。
**毎日の支出ではなく「予算を超えた」という例外だけに付く**ので、
一覧が警告だらけにはならない。

`pnpm check:contrast` に「超過の棒 / 下地」を追加し、両モードで 3:1 以上を確認した。

#### マイグレーションの安全性

`0004_budgets` は**追加のみ**で、既存テーブルに一切触らない。
ローカルの捨て DB に適用して次を確認した。

| 確認したこと | 結果 |
| --- | --- |
| CHECK（0 円 / 負数 / 上限+1） | すべて `23514` で弾かれる |
| 一意制約（同じカテゴリに 2 件） | `23505` で弾かれる |
| カテゴリを消したら予算も消える | cascade する |
| 世帯を消したら予算も消える | cascade する |

`anon` / `authenticated` への権限は
[0002 の `alter default privileges`](../02-design/database-design.md#将来のテーブルも守られる)
が打ち消しているので、このテーブルにも付かない。
**本番適用後に [テスト戦略 §4.2](../03-guidelines/testing-strategy.md#42-認可の確認毎回実施) の確認で 0 件であることを見る。**

### Tier 3: 定期支出 — **手動トリガー版まで**

| | 実装する | 実装しない（理由） |
| --- | --- | --- |
| 定期支出 | **「定期」の印 + 先月分をまとめて登録** | **自動実行はデプロイ後。** Cron はホスティングに依存する |
| リマインド通知 | — | **デプロイ先が未決のため実装できない。** プッシュには公開 HTTPS と VAPID 鍵が必要で、検証する手段が無い |

**仕組みを先に作る。** 「先月の定期支出を今月に写す」処理を Server Action
として用意しておけば、デプロイ後に Cron から同じ関数を呼ぶだけになる。

| 事項 | 決定 |
| --- | --- |
| 印の持ち方 | `Transaction.recurring`（boolean）。**別テーブルにしない** |
| なぜ別テーブルにしないか | 「定期のルール」を独立して持つと、金額の変更・終了日・頻度（毎月/毎年）まで設計が広がる。**写した記録にも印が付くので、翌月も同じ仕組みで動く** |
| 日付 | 先月と同じ日。その月に存在しない日（1/31 → 2 月）は**その月の末日**に寄せる |
| 二重登録 | **同じカテゴリ・同じ金額の記録が今月に既にあれば写さない** |
| 自動化の余地 | 同じ処理を Cron から呼べるように、判定も純関数に出す |

## 見直す条件

| 条件 | 対応 |
| --- | --- |
| デプロイ先が決まった | 定期支出の自動実行（Cron）とリマインド通知を実装する |
| 月ごとに違う予算を立てたくなった | `budgets` を `(household_id, category_id, month)` に広げる。既存行は「既定値」として残す |
| 3 人以上で精算したくなった | 精算の分担方法（均等 / 収入比）を選べるようにする。別 ADR |
| 定期支出の金額が毎月変わる（電気代など） | 「前回の金額」を初期値にして確認を挟む形に変える |
| 予算の超過を通知したくなった | リマインド通知と同じ仕組みに乗せる（デプロイ後） |

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 予算を月ごとに持つ | 画面と設計が重くなる。まず「毎月同じ額」で足りるか確かめる |
| 予算の設定をカテゴリ管理の画面に混ぜる | 1 行に改名・非表示・予算の 3 つが並び、操作を間違えやすい |
| 予算を 1 件ずつ保存する | 13 カテゴリで 13 回の送信になる |
| 予算なしを別の削除ボタンで消す | 空欄か 0 で消えるほうが操作が少ない |
| 定期支出を別テーブル（ルール）で持つ | 終了日・頻度・金額変更まで設計が広がる。印 1 つで翌月も動く形で足りるか先に確かめる |
| 定期支出を Cron で自動登録する（今回） | **デプロイ先が未決。** 検証できないものを入れない |
| リマインド通知を実装する | 同上。公開 HTTPS と VAPID 鍵が無いと動作確認ができない |
| 支出全体に対する予算（カテゴリなし） | どこを削ればよいか分からない。カテゴリ別のほうが行動に繋がる |
| 精算を 3 人以上に対応させる | 分担方法の選択肢が増え、v1 の範囲を超える |
